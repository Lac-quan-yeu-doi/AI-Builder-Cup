# GCP production environment

This root creates a production environment independent from `gcp-dev` while
in the dedicated `celesnity-minder-platform` project in London.

## Production boundaries

- Regional GKE cluster: `celesnity-gcp-prod` in `europe-west2`.
- Three application nodes and three dedicated streaming nodes initially: one of
  each per zone, autoscaling the application pool up to six nodes total.
- Regional Cloud SQL instance: `celesnity-gcp-prod-postgres`, with automated
  backups, 14 retained backups, PITR, and deletion protection.
- Separate warehouse, artifacts, Loki, Terraform-state buckets, and Artifact
  Registry repositories, all carrying the `gcp-prod` prefix.
- Three Redpanda and three EMQX replicas. Redpanda uses zone rack awareness and
  TLS issued by the in-cluster cert-manager installation.
- Broker node boot disks and broker persistent volumes use `pd-standard` through
  the production-only `celesnity-gcp-prod-broker-data` CSI StorageClass. The lean
  initial profile allocates 150 GiB to Redpanda and 60 GiB to EMQX across their
  three replicas. Dedicated broker nodes use `e2-standard-4`; this lean profile
  avoids depending on the scarcer N2 pool while retaining four vCPUs per node.

The committed `terraform.tfvars.example` is deliberately non-secret and is the
input used by `cloudbuild.yaml`. Do not create a local production state file or
commit a different tfvars file.

## Operator prerequisites

Before an apply build:

1. Create two global Certificate Manager certificates:
   - `celesnity-prod-https`, covering `app.celesnity.com`,
     `control.celesnity.com`, `trino.celesnity.com`,
     `api.celesnity.com`, and `grafana.celesnity.com` (or the equivalent
     `*.celesnity.com` wildcard);
   - `celesnity-prod-mqtt`, covering only `mqtt.celesnity.com`.
2. Configure the Cloud Build service account using `cloudbuild-setup.sh` as a
   reviewed command reference; execute the equivalent commands as a project IAM
   administrator. This also enables the APIs required by the first build.
   Then run `apps-cloudbuild-setup.sh` for the separate least-privilege account
   used by the four application release triggers.
3. Create the production release trigger against `cloudbuild.yaml`. It matches
   semantic version tags (`v1.2.3`), sets `_ACTION=apply`,
   `_CONFIRM_TARGET=celesnity-gcp-prod`, and `_REQUIRE_RELEASE_TAG=true`.
   For `v0.1.0`, create the tag only from the reviewed `release/0.1.0` head;
   Cloud Build tag triggers do not independently prove branch ancestry.
4. Restrict who can create release tags or edit the trigger. A successful apply build has
   infrastructure-administrator privileges.
5. Before the application builds, create the production-only runtime values that
   Terraform cannot derive:
   - `gcp-prod-minder-llm-base-url`
   - `gcp-prod-minder-llm-api-key`
   - `gcp-prod-control-plane-iap-client-id`
   - `gcp-prod-control-plane-iap-client-secret`

   Never copy any of these values from development. Terraform derives and
   versions `gcp-prod-minder-database-url` from the production private Cloud SQL
   instance and requires encrypted transport.

   Customer owners are not bootstrapped through a Core allowlist. The
   Celesnity-only Control Plane provisions each Identity Platform tenant and
   persists its initial `ORG_OWNER` membership before the customer can sign in.

### Release 0.4.0 existing-organization tenant cutover

The existing production `celesnity` organization is bound to a different
Identity Platform tenant than the one originally generated by this Terraform
module. For release 0.4.0, the approved tenant is the one already bound to that
organization. It is stored as immutable version `2` of
`gcp-prod-identity-platform-tenant-id`; `identity_tenant_id_source_version`
pins that version. Terraform reads the pinned version and publishes the same
tenant ID in later versions, so an Infra apply cannot silently switch Web/Core
back to the generated tenant. The generated tenant remains managed but unused;
do not delete it during this release. Its eventual retirement needs a separate
user and tenant inventory.

The selected existing tenant has its own authentication policy; the generated
tenant's MFA setting does not transfer with the Secret Manager ID. At the
2026-09-26 preflight, the selected tenant reported MFA `DISABLED` and the
approved owner had no enrolled factor. Record an explicit security decision
and an enrollment plan before requiring MFA in production; do not assume this
change enables it.

Before tagging or deploying, verify that version `2` is enabled and matches
the live `celesnity` organization's `identity_tenant_id`, and that the approved
bootstrap owner subject exists, is enabled, and has the matching email in that
tenant. Do not infer the subject from the email. The six
`gcp-prod-auth-bootstrap-*` secrets must each have an enabled, nonempty latest
version matching that same live organization and owner. These values are
deployment inputs, not a request to create another organization or owner.

Promote the matching Infra and Core release changes together, then deploy in
this order: Infra, Core, Web, Agent. Core's migration/bootstrap Job must finish
before its API and worker rollout; an existing organization with several active
owners is verified against the selected owner rather than given a new owner.
Review the saved Terraform plan before Infra apply and reject any tenant
deletion, replacement, or unexpected Secret Manager changes. This cutover does
not reset `celesnity_app` or deploy production merely by merging code.

Cloud Build creates and versions the remote state bucket, initializes the GCS
backend, creates the foundation in the first Terraform stage, applies one saved
full plan, idempotently creates the generated Core credential, audit, FTPS,
chart-sharing, and GCS HMAC secrets, builds the Spark image, and deploys the
`gcp-prod` Kustomize overlay. Secret
values are never printed to the build log.

After the apply succeeds, create the Cloudflare records using the
`trino_lb_address` and `mqtt_load_balancer_ip` Terraform outputs shown in the
build log or queried from a controlled administrative build.

## Application trigger substitutions

Use these production substitutions for Core, Web, Control Plane, and Agent:

```text
_AR_HOST=europe-west2-docker.pkg.dev
_AR_REPO=celesnity-gcp-prod-apps
_CLUSTER=celesnity-gcp-prod
_CLUSTER_LOCATION_TYPE=region
_CLUSTER_LOCATION=europe-west2
_NAMESPACE=celesnity-prod
_ENV=gcp-prod
_MOVING_TAG=production-latest
```

The Web trigger also requires:

```text
_CORE_API_URL=https://api.celesnity.com/api/v1
```

The Agent trigger additionally uses `_NAMESPACE=minder-prod` and
`_WORKLOAD_NAMESPACE=celesnity-prod`. The Control Plane trigger sets
`_CLOUD_ARMOR_POLICY=celesnity-gcp-prod-web` and
`_GSA_EMAIL=celesnity-gcp-prod-control-pla@celesnity-minder-platform.iam.gserviceaccount.com`.
The shortened account ID is Terraform's deterministic 30-character GCP service
account limit; obtain it from `workload_google_service_accounts` rather than
reconstructing it from the Kubernetes service-account name.
